# 公司综合管理应用差异清单与开发路线图

## 1. 结论

当前项目建议继续迭代，不建议整体重写。

原因：

- 现有系统已经具备员工、工资、绩效、部门、公司、客户、项目、合同、业务、订单、财务、报表、导入导出等主体模块。
- 目标业务主链路“项目 -> 合同 -> 订单 -> 财务 -> 回写合同/项目/统计”与现有系统方向一致。
- 核心数据模型已具备大部分基础字段，主要问题是字段完整度不足、统计口径不统一、认证与工程质量偏弱。

建议采用“保留现有前后端框架与主业务表，做结构化升级”的方式推进。

## 10. 2026-04-23 补充业务确认

### 10.1 公司多银行账户

已确认：

- 一家公司确实存在多个银行账户
- 当前数据库 `bank_accounts` 已有实际数据，可继续采用“一家公司对多银行账户”的结构

设计结论：

- `Company` 继续作为公司主体表
- `BankAccount` 继续作为公司银行账户子表
- 合同、财务记录都应关联具体 `bank_account_id`
- 同时保留 `bank_account_name`、`bank_account`、`bank_name` 等冗余快照字段，避免后续账户信息修改影响历史单据

页面建议：

- 公司详情页展示“公司基础信息 + 银行账户列表”
- 合同新增/编辑时必须选择一个收款账户
- 财务收款记录默认继承合同收款账户，但允许在录入时手工调整

### 10.2 新核心链路确认

当前确认的主流程应调整为：

1. 建立项目
2. 建立合同
3. 新建订单
4. 订单完成后生成请款单
5. 财务管理生成请款数据
6. 合同、项目同步累计请款金额
7. 财务管理登记收款
8. 订单管理标识对应订单已收款
9. 绩效管理生成员工绩效
10. 合同、项目同步累计收款金额与绩效金额

该流程说明：

- “请款”与“收款”是两个不同业务事件，不能混为一个字段状态
- 绩效生成应发生在“订单已收款”之后，而不是订单创建后立即生成

### 10.3 请款单设计建议

为了让“请款金额”和“收款金额”口径清晰，建议新增独立的请款单实体，而不是完全依赖财务表兼容。

建议增加：

- `payment_requests` 请款单表

建议字段：

- ID
- 请款单号
- 订单ID
- 订单编号
- 合同ID
- 合同编号
- 项目ID
- 项目编号
- 项目名称
- 客户ID
- 客户名称
- 公司ID
- 公司名称
- 部门ID
- 部门名称
- 请款日期
- 请款金额
- 请款状态
- 来源快照金额

推荐状态：

原因：

- 请款是应收推进动作，不等于财务到账
- 一个订单可能多次请款、分次收款
- 后续对账、报表、回写、变更追踪会更稳定

### 10.4 财务管理与请款的关系

建议关系：

- 请款单负责记录“向客户发起请款”
- 财务记录负责记录“实际收入/支出”

财务收入记录建议增加来源字段：

- `source_type`：如 `payment_request`、`manual`
- `source_id`
- `order_id`
- `order_no`
- `project_id`
- `customer_id`

这样可以稳定实现：

- 一笔收款对应哪个请款单
- 一笔收款最终对应哪些订单
- 合同、项目、员工绩效的金额如何追溯

## 11. 绩效管理重构建议

### 11.1 绩效生成原则

按当前确认业务，绩效应以“收款完成”为主要触发条件，而不是单纯按订单创建或订单完成触发。

推荐规则：

- 订单完成后，只具备“可请款”资格，不生成绩效
- 请款后，只累计合同/项目的请款金额，不生成绩效
- 财务登记收款后，才允许生成绩效
- 如果是部分收款，则按收款比例生成对应绩效

### 11.2 绩效表建议口径

当前数据库 `performance` 为空，可以直接按更合理的方式使用。

建议将绩效分成两层：

1. `performance_details` 或直接重构 `performance` 为绩效明细表
2. 员工绩效报表按明细实时汇总，不单独再维护复杂月表

建议绩效明细字段：

- ID
- 员工ID
- 员工名称
- 日期
- 订单ID
- 订单编号
- 合同ID
- 合同编号
- 项目ID
- 项目编号
- 部门ID
- 部门名称
- 公司ID
- 公司名称
- 绩效基数金额
- 绩效费率
- 绩效金额
- 来源类型
- 来源ID
- 状态
- 备注

### 11.3 绩效计算建议

订单维度建议保留：

- `total` 订单合计
- `settlement_fee` 结算费
- `performance_fee` 绩效费

建议绩效计算公式明确为：

- 订单绩效基准金额 = `total * performance_fee / 100`
- 如果订单分次收款：
  绩效已生成金额 = 订单绩效基准金额 * 累计收款金额 / 订单应收或订单合计

如存在更明确口径，后续可在实施前最终锁定：

- 按订单合计计算
- 按订单结算金额计算
- 按订单实际收款比例计算

当前更推荐：

- “按实际收款比例计算绩效”

因为这样最符合财务闭环，也最能避免未收款先发绩效。

## 12. 订单变更后的全链路回写规则

### 12.1 订单变更分类

订单变更不能一刀切处理，建议分为三类：

1. 未生成请款单前的订单变更
2. 已生成请款单但未收款前的订单变更
3. 已发生收款后的订单变更

### 12.2 各阶段处理规则

#### A. 未生成请款单前

允许直接修改订单。

修改后自动回写：

- 订单合计
- 订单绩效金额
- 合同累计金额
- 项目累计金额

#### B. 已生成请款单但未收款前

允许修改，但必须同步回写请款单和上层汇总。

修改后自动回写：

- 订单合计
- 订单绩效基准金额
- 未完成的请款单金额
- 合同请款金额
- 项目请款金额
- 合同汇总金额
- 项目汇总金额

建议增加校验：

- 若订单新金额小于已确认请款金额，则不允许直接保存，必须先处理请款单

#### C. 已发生收款后

不建议允许直接“覆盖式修改”。

建议改成两种方式：

- 发起订单变更单
- 或允许修改，但系统自动记录差额并触发重算

修改后必须处理：

- 已收款金额是否超过新订单金额
- 已生成绩效是否超出新应得绩效
- 合同、项目累计金额是否需要调整
- 是否生成“待人工确认”的异常状态

### 12.3 推荐的系统行为

最稳妥的实现方式：

- 订单保存时系统重算订单级派生金额
- 系统根据订单当前关联的请款、收款、绩效记录生成差异值
- 若下游还未锁定，则自动同步
- 若下游已锁定或已入账，则标记“需人工处理”

建议新增字段：

- 订单：`calc_version`、`is_dirty`
- 请款单：`snapshot_total`、`snapshot_performance_fee`
- 绩效：`snapshot_total`、`snapshot_received_amount`

这样每次变更都能知道：

- 当时生成请款或绩效时参考的原始订单金额是多少
- 现在订单金额变更后差异是多少

## 15. 2026-04-23 绩效归属与权限确认

### 15.1 绩效归属规则

已确认：

- 绩效只分给业务员
- 不按负责人分配绩效
- 不做多员工拆分绩效

设计结论：

- 订单必须有明确 `salesman`
- 绩效生成时默认归属该订单的业务员
- 如果订单无业务员，则该订单不可生成绩效，需提示补全数据

推荐口径：

- `orders.salesman` 保存业务员名称
- 同时建议补充 `salesman_id`
- 绩效明细保存 `employee_id`、`employee_name`、`order_id`、`contract_id`、`project_id`

### 15.2 业务员角色设计

已确认：

- 员工权限增加“业务员”角色
- 业务员只能查看自己负责的项目、合同、订单、请款、统计表等

建议角色枚举：

- `admin`
- `manager`
- `sales`
- `staff`

各角色建议权限：

- `admin`：全量管理权限
- `manager`：查看全量业务数据，可管理大部分业务数据，但权限低于管理员
- `sales`：只能查看和自己相关的数据
- `staff`：普通员工，仅查看自身基础信息、工资、绩效等个人数据

### 15.3 业务员数据范围规则

业务员 `sales` 的可见范围建议统一定义为：

- 项目：`salesman_id = 当前用户ID` 或 `salesman = 当前用户名`
- 合同：同上
- 订单：同上
- 请款单：来源订单属于当前业务员
- 绩效：仅查看自己的绩效
- 员工报表：仅查看自己的个人报表
- 公司/部门/项目/合同统计报表：仅展示与本人相关数据的聚合结果

实现建议：

- 后端统一增加数据范围过滤器
- 不要只在前端隐藏按钮，必须在接口层限制

为支持业务员权限与绩效归属，建议补充：

- `contracts.salesman_id`
- `orders.salesman_id`
